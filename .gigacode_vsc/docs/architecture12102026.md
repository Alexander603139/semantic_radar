# Итоговая архитектура приложения «Семантический радар» на 12.10.2026

## 1. Назначение системы

Система автоматически собирает статьи/вакансии с заданных источников, семантически фильтрует их по заданному контексту (через косинусное сходство эмбеддингов), векторизует прошедшие фильтр статьи, анализирует дрейф тем и генерирует отчёты. Управление — через веб-админку, доступную по адресу https://lithef.twc1.net.

## 2. Микросервисы

| Сервис | Порт | Роль | Что делает |
|---|---|---|---|
| ingestor | 8003 | Оркестратор пайплайна | Парсит источники, вызывает context_filter, сохраняет статьи, запускает векторизацию, запускает анализ/отчёт по расписанию |
| embedder | 8004 | Векторизация | Разбивает статьи на чанки, строит эмбеддинги, сохраняет в Parquet; также векторизует тексты без сохранения (для фильтра) |
| analyzer | 8005 | Анализ | Кластеризует векторы и считает дрейф тем между неделями |
| reporter | 8006 | Отчёты | Генерирует HTML-отчёт по результатам анализа |
| storage | 8007 | Хранилище + настройки | Хранит файлы (статьи/векторы/отчёты) в S3 + метаданные в PostgreSQL; настройки пользователя; реестр AI-моделей |
| traffic_stats | 8009 | Метрики доменов | Запрашивает Open Page Rank + проверяет HTTP-доступность сайтов |

## 3. Инфраструктура

### 3.1. Reverse proxy — системный nginx

Конфиг расположен в `/etc/nginx/sites-available/lithef.twc1.net` (вне репозитория). Маршрутизация:

| Путь | Куда |
|---|---|
| `/` | Frontend (статика из `/opt/semantic-radar`) |
| `/ingestor/` | 127.0.0.1:8003 |
| `/embedder/` | 127.0.0.1:8004 |
| `/analyzer/` | 127.0.0.1:8005 |
| `/reporter/` | 127.0.0.1:8006 |
| `/storage/` | 127.0.0.1:8007 |
| `/reports/` | 127.0.0.1:8007/download/ |
| `/traffic_stats/` | 127.0.0.1:8009 |
| `/context_filter/` | 127.0.0.1:8010 |

**Безопасность на уровне nginx:**

- HTTPS через Let's Encrypt (Certbot)
- Редирект HTTP → HTTPS
- Блокировка доступа к `.env`, `.git`, `*.yml`, `*.yaml`, `*.bak`, `*.sql`, `*.md`, `*.json`
- Заголовки `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`

### 3.2. Базы данных и хранилища

- **PostgreSQL** — реляционные данные: метаданные файлов (files), настройки пользователей (user_settings), реестр AI-моделей (ai_models)
- **S3-совместимое объектное хранилище** (MinIO локально или Yandex Object Storage в продакшене) — бинарные файлы: Parquet-векторы, JSON-статьи, HTML-отчёты. Конфигурация через `.env`: `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET_NAME`, `S3_REGION`

### 3.3. Фронтенд

Статическая админка (`index.html` + `app.js` + `style.css`), размещается в `/opt/semantic-radar` на хосте, отдаётся nginx напрямую.

### 3.4. Контейнеризация и деплой

- Docker Compose
- GitHub Actions для CI/CD на сервер msk-1-vm-39kb

## 4. Основной поток данных (пайплайн парсинга)

### Отдельные потоки:

- **Анализ:** analyzer ← векторы из storage → дрейф тем (UMAP + HDBSCAN + Wasserstein)
- **Отчёт:** reporter ← результат анализа → HTML-отчёт в storage
- **Измерение сайтов:** фронтенд → traffic_stats/analyze (Open Page Rank + доступность)

## 5. Ключевые архитектурные решения

### 5.1. Двойная векторизация (осознанный выбор)

Первый раз — в context_filter: статьи целиком (1 вектор на статью) для сравнения с контекстом.
Второй раз — в embedder: статьи чанками (N векторов) для сохранения в Parquet.

**Причина:** context_filter работает с целыми статьями, а embedder/analyzer — с чанками. Размерности не совпадают, поэтому переиспользовать векторы нельзя.

### 5.2. Маппинг body ↔ text между сервисами

У каждого сервиса своя модель Article:

- ingestor: поле `body: str`
- embedder: поле `text: str`
- context_filter: поле `body: str`

Преобразование выполняется вручную в `services/ingestor/src/embedder_client.py` при формировании JSON для вызова embedder: `art.body → "text"`. Также поддерживается мок (`EMBEDDER_MOCK=true` в `.env` ingestor) для изолированного тестирования.

### 5.3. Конфигурация через storage

Настройки пользователя (таблица `user_settings` в PostgreSQL):

- `sources` — список сайтов
- `schedule_cron`, `timezone` — расписание
- `context`, `threshold` — семантический фильтр
- `active_model_slug` — активная AI-модель
- `last_fallback_event` — последнее событие fallback

### 5.4. Реестр AI-моделей

Хранится в PostgreSQL (таблица `ai_models`). Поддерживаются два типа провайдеров:

- `local_huggingface` (локальные HuggingFace-модели)
- `openai_api` (внешние API, например, Яндекс через Timeweb proxy)

### 5.5. Fallback-логика в embedder (Этап 7)

Два слоя fallback на локальную e5-base-local:

- Если у API-модели нет ключа → сразу fallback.
- Если API-модель упала при векторизации (таймаут, 5xx, ошибка сети) → fallback.

Событие fallback записывается в `storage.last_fallback_event` и отображается в админке.

### 5.6. Защита от смены модели при наличии векторов

В админке кнопка «Сохранить активную модель» блокируется, если в storage уже есть векторы (разные модели дают несовместимые размерности). Требуется сначала удалить старые векторы через UI.

### 5.7. Устойчивый парсинг (пункт "в")

- Ошибка на одном источнике не останавливает всю задачу
- Собирается два списка: `failed_sources` (ошибки сети/недоступные) и `empty_sources` (парсер не нашёл статей)
- В результате задачи возвращается полная статистика: собрано / прошло фильтр / отклонено / пустые / недоступные
- UI выводит предупреждения после завершения задачи

### 5.8. Двойное хранение файлов (S3 + PostgreSQL)

| Что | Где |
|---|---|
| Бинарные файлы (Parquet, HTML, JSON-статьи) | S3-совместимое объектное хранилище |
| Метаданные файлов (user_id, file_type, file_key, storage_path, checksum, extra_metadata) | PostgreSQL, таблица files |

### 5.9. Изоляция векторов по моделям в S3 (Этап 8)

Векторы физически лежат в разных папках S3-бакета в зависимости от `model_slug`:

```
s3://bucket/model_slug_1/vectors.parquet
s3://bucket/model_slug_2/vectors.parquet
s3://bucket/model_slug_3/vectors.parquet
...
```

Это позволяет хранить векторы от разных моделей без пересечений и легко фильтровать по `model_slug`.

## 8. Алгоритм дрейфа тем (Topic Drift)

Трёхэтапный пайплайн в analyzer:

### Этап 1: Кластеризация

- Загрузка эмбеддингов из Parquet
- StandardScaler (нормализация)
- UMAP — снижение размерности с 768 до 5
- HDBSCAN — кластеризация по плотности (`min_cluster_size=5`)

### Этап 2: Расчёт drift_score

- Метрика: усреднённое одномерное расстояние Вассерштейна (1D EMD) по всем измерениям эмбеддинга
- Формула: `drift_score = (1/D) × Σ W₁(P_d_old, P_d_new)` для d = 1..D
- Библиотека: `scipy.stats.wasserstein_distance`
- Нормализация: отсутствует — значение не ограничено диапазоном [0, 1]

### Этап 3: Определение сдвинутых тем

- Извлечение топ-N терминов через `collections.Counter`
- Удаление русских стоп-слов
- Наивное позиционное сравнение списков терминов кластеров по порядку (не по центроидам и не по similarity)

**Известные ограничения (из backlog):**

- Нет нормализации drift_score (docstring говорит 0..1, код возвращает raw mean EMD)
- Per-dimension EMD вместо истинного многомерного
- Сравнение тем по индексу в словаре, а не по центроидам
- Модуль `drift.py` пустой (0 строк)
- Нет визуализации кластеров (UMAP-координаты не возвращаются клиенту)

## 9. Известные ограничения и backlog

1. **Аутентификация** — добавить JWT через user_manager (во всех 6 сервисах)
2. **drift.py** — выделить логику дрейфа в отдельный модуль
3. **Нормализация drift_score** — привести к диапазону [0, 1]
4. **Визуализация кластеров** — возвращать UMAP-координаты клиенту
5. **Локальные модели** — e5-base-local и minilm-local показывают аномально высокое сходство для разных тем; требуется замена или тюнинг
6. **Валидация URL на фронте** — сейчас можно ввести невалидные адреса (ht1trnal.com) и запустить парсинг; реализуется только через отчёт о недоступных/пустых сайтах
